# HORROR-GAME-PROJECT

Unity 기반 1인칭 3D 공포게임 프로젝트입니다.  
2인이 협업하여 개발했으며, 직접 제작한 맵을 Unity 씬으로 구성하고 플레이어 탐색, 아이템 획득, 오브젝트 상호작용, 퍼즐, 이벤트 연출을 연결해 하나의 플레이 흐름으로 구현했습니다.

`HORROR-GAME-PROJECT`는 어두운 공간을 탐색하며 아이템을 획득하고, 잠긴 문과 퍼즐을 해결하면서 다음 구역으로 진행하는 구조의 공포게임입니다.

단순히 갑작스러운 점프스케어에 의존하기보다, 제한된 시야, 조명, 사운드, 공간 구조, 이벤트 트리거를 조합해 탐색 과정에서 긴장감이 쌓이도록 구성했습니다.

## 개발 배경

이 프로젝트에서 가장 중요하게 생각한 부분은 **직접 제작한 맵을 실제 게임플레이가 가능한 공간으로 만드는 것**이었습니다.

맵은 단순한 배경이 아니라 플레이어의 이동 경로, 아이템 배치, 문과 잠긴 문, 퍼즐 오브젝트, 이벤트 발생 지점을 결정하는 핵심 요소였습니다.  
따라서 맵 제작 단계부터 플레이어가 어떤 순서로 공간을 탐색하고, 어디서 긴장감을 느끼며, 어떤 조건을 만족해야 다음 단계로 진행할 수 있는지를 함께 고려했습니다.

개발 과정에서 중점적으로 본 부분은 다음과 같습니다.

- 플레이어가 어두운 공간을 탐색하며 자연스럽게 목표를 찾도록 동선 구성
- 아이템 획득, 문 상호작용, 퍼즐 해결이 이어지는 진행 흐름 설계
- 손전등과 조명을 활용한 제한된 시야 연출
- 특정 위치 또는 조건에서 이벤트가 발생하도록 맵과 시스템 연결
- 2인 협업 과정에서 기능을 나누어 구현하고 Unity 씬에 통합

## 팀 구성 및 기여 정리

이 프로젝트는 2인이 함께 개발했습니다.  
맵 제작은 제가 직접 담당했으며, 구현은 팀원과 거의 함께 진행했습니다.

다만 원본 프로젝트의 commit 기록만으로 개인별 구현 범위를 정확히 나누기는 어렵습니다.  
개발 당시 Unity 씬과 프리팹 merge 과정에서 문제가 자주 발생했고, 제가 작업한 내용을 Zip 파일로 전달한 뒤 팀원 계정에서 다시 commit한 경우가 있었습니다.

그 결과 팀원의 commit 수가 더 많게 보이지만, 실제 작업 비중을 commit 횟수만으로 판단하기는 어렵습니다.  
따라서 이 문서에서는 개인 담당이 명확한 영역과 협업 구현 영역을 구분해 정리했습니다.

### 개인 담당으로 명확한 영역

- SketchUp을 활용한 맵 제작
- Unity 내 레벨 구성
- 공간 구조, 복도, 방, 문, 이동 동선 설계
- 오브젝트 배치
- 조명과 어두운 구간을 활용한 분위기 구성

### 협업 구현 영역

- 플레이어 이동과 시점 제어
- 손전등과 입력 처리
- Raycast 기반 상호작용
- 문, 잠긴 문, 서랍, 아이템, 스위치, 모니터, 금고, 환풍구 상호작용
- 인벤토리와 아이템 상태 관리
- 튜토리얼 진행
- 퍼즐 조건 처리
- 병원 구역 이벤트, 추격 이벤트, 히든 이벤트
- UI, 타이틀, 일시정지, 엔딩 흐름
- 사운드와 애니메이션 연출

## 주요 기능

### 1. 맵 / 레벨 제작

맵은 직접 제작한 3D 모델을 Unity로 가져와 플레이 가능한 레벨로 구성했습니다.

단순히 모델을 배치하는 것이 아니라, 플레이어가 이동하고 조사하고 이벤트를 경험할 수 있도록 공간을 게임 흐름에 맞춰 정리했습니다.

주요 구성 요소는 다음과 같습니다.

- 교실, 복도, 문, 엘리베이터, 병원 계열 공간으로 이어지는 탐색 구조
- 튜토리얼 구간과 본 게임 구간의 연결
- 아이템 획득 위치와 잠긴 문 배치
- 퍼즐 오브젝트와 이벤트 트리거 위치 구성
- 조명과 어두운 공간을 활용한 공포 분위기 연출

### 2. 플레이어 탐색 흐름

플레이어는 1인칭 시점으로 맵을 탐색하며, 필요한 아이템을 얻고 오브젝트와 상호작용해 다음 단계로 진행합니다.

기본 흐름은 다음과 같습니다.

1. 튜토리얼에서 이동과 상호작용 학습
2. 맵 탐색 중 아이템 획득
3. 문, 잠긴 문, 서랍, 모니터, 금고 등과 상호작용
4. 퍼즐 또는 이벤트 조건 해결
5. 새로운 구역으로 이동
6. 추격, 히든 이벤트, 엔딩 흐름으로 연결

### 3. Raycast 기반 상호작용

플레이어가 바라보는 방향으로 Raycast를 사용해 오브젝트를 감지하고, 감지된 대상의 태그와 컴포넌트에 따라 상호작용을 처리했습니다.

이 구조를 통해 다양한 오브젝트를 같은 입력 흐름 안에서 처리할 수 있었습니다.

상호작용 대상 예시는 다음과 같습니다.

- 문 / 잠긴 문 / 비밀 문
- 서랍
- 아이템
- 모니터 / 키보드 / 빔프로젝터
- 금고 / 숫자 금고
- 스위치 / 버튼
- CCTV
- 환풍구
- 소각로
- 이벤트 오브젝트

### 4. 인벤토리와 아이템 진행

아이템 획득 여부를 상태 값으로 관리하고, 특정 아이템 보유 여부에 따라 문, 퍼즐, 이벤트 진행이 달라지도록 구성했습니다.

구현 흐름은 다음과 같습니다.

- 아이템 오브젝트와 상호작용
- 아이템 획득 상태 갱신
- 인벤토리 슬롯에 아이템 정보 표시
- 현재 선택한 아이템 이미지 표시
- 아이템 보유 여부에 따라 잠긴 문 또는 이벤트 진행

### 5. 퍼즐 / 이벤트 시스템

게임 진행 중 특정 오브젝트의 상태나 플레이어의 위치에 따라 퍼즐과 이벤트가 발생합니다.

프로젝트 내에서 확인되는 대표 구현 요소는 다음과 같습니다.

- 모니터 On/Off 조합 퍼즐
- 숫자 금고 입력 퍼즐
- 스크린 퍼즐
- 라이터와 조명 관련 이벤트
- 병원 구역 이벤트
- 의사 추격 및 플레이어 사망 처리
- 소각로, 비밀 방, 히든 이벤트
- 엔딩 및 엔딩 크레딧 흐름

### 6. 공포 분위기 연출

공포 분위기는 공간, 조명, 사운드, 이벤트 타이밍을 조합해 구성했습니다.

- 어두운 맵과 제한된 시야
- 손전등을 통한 시야 확보
- 조명 On/Off 변화
- 발소리, 문 소리, 아이템 획득음, 이벤트 사운드
- 갑작스러운 출현보다 탐색 중 압박감이 쌓이는 흐름
- 추격 이벤트와 히든 이벤트를 통한 긴장감 강화

## 구현 관점에서 정리한 핵심 포인트

### 맵을 중심으로 게임 흐름 설계

직접 제작한 맵을 기준으로 플레이어의 이동 경로, 아이템 위치, 문과 잠긴 문, 퍼즐 오브젝트, 이벤트 트리거를 배치했습니다.

맵이 단순 배경으로 끝나지 않고, 게임 진행을 제어하는 구조가 되도록 구성한 점이 핵심입니다.

### 하나의 입력 흐름으로 여러 상호작용 처리

Raycast 기반으로 오브젝트를 감지하고, 오브젝트 종류에 따라 상호작용을 분기했습니다.

이를 통해 문 열기, 아이템 획득, 금고 조작, 모니터 조작, 환풍구 상호작용 등을 같은 탐색 흐름 안에서 처리할 수 있었습니다.

### 상태 기반 진행 관리

아이템 보유 여부, 퍼즐 완료 여부, 이벤트 완료 여부를 상태 값으로 관리했습니다.

특정 조건을 만족해야 다음 구역으로 이동하거나 다음 이벤트가 실행되도록 구성했습니다.

### 협업 과정에서 얻은 개선점

Unity 프로젝트는 씬과 프리팹 충돌이 자주 발생하기 때문에, 당시처럼 Zip 파일로 전달하고 한 명이 다시 commit하는 방식은 이력 관리에 한계가 있었습니다.

이 프로젝트를 다시 제작한다면, 다음과 같은 사항들을 고려해볼 것 같습니다.

- 기능 단위 브랜치와 Pull Request 사용
- 씬 또는 프리팹 담당 범위 사전 분리
- Unity Smart Merge 설정 적용
- 공통 씬 수정 전후 변경 범위 공유
- Git LFS로 대용량 바이너리 에셋 관리
- commit message에 실제 작업 범위 명확히 기록
- Zip 전달 대신 branch, patch, PR 기반으로 변경사항 공유

### 코드 구조 개선 방향

프로젝트를 다시 정리하면서 확인해보니, 기능 자체는 동작하도록 구현되어 있지만 이벤트성 스크립트가 지나치게 많이 분리되어 있는 부분이 있었습니다.  
특히 `HospitalMap` 폴더에는 특정 상황 하나를 처리하기 위한 스크립트가 여러 개 존재합니다.

예를 들어 특정 트리거에 들어가면 오브젝트를 끄는 `ColliderOff`, 의사 오브젝트를 비활성화하는 `DissapearAI`, 플레이어가 들어오면 의사와 이벤트 오브젝트를 켜는 `DoctorSayHI`, 특정 위치에서 조명을 켜는 `ShowerRoomLightOn`, 사운드 오브젝트를 켜고 끄는 `STOP`, `Stop_Stop` 같은 스크립트들이 각각 따로 작성되어 있습니다.

이 스크립트들은 대부분 공통적으로 다음과 같은 단순 동작을 수행합니다.

- 특정 Trigger 또는 Collision 감지
- Player 또는 Doctor 태그 확인
- 특정 GameObject 활성화 / 비활성화
- 사운드 또는 조명 오브젝트 On/Off
- 한 번 실행 후 자기 자신 비활성화
- 간단한 안내 텍스트 출력

당시에는 빠르게 이벤트를 붙이고 씬에서 바로 확인하는 방식으로 개발했기 때문에 기능별 스크립트가 계속 늘어났습니다.  
하지만 지금 기준에서 보면, 이런 단순 이벤트 로직은 각각 별도 클래스로 만들기보다 Unity의 Inspector와 `UnityEvent`를 활용한 범용 Trigger Event 컴포넌트로 통합하는 편이 더 적절했습니다.

예를 들어 `TriggerEventHandler` 같은 공통 스크립트를 만들고, `OnTriggerEnter`, `OnTriggerExit`, `OnCollisionStay` 같은 이벤트 시점에 실행할 동작을 Inspector에서 연결했다면 다음과 같은 장점이 있었을 것입니다.

- 비슷한 스크립트 중복 제거
- 이벤트 추가 시 새 C# 파일을 만들 필요 감소
- 씬에서 어떤 오브젝트가 켜지고 꺼지는지 Inspector 기준으로 확인 가능
- 기획 변경 시 코드 수정 없이 UnityEvent 연결만 변경 가능
- 특정 맵 전용 스크립트가 늘어나는 문제 완화

또한 상호작용 시스템도 개선 여지가 있었습니다.  
프로젝트에는 `IInteraction` 인터페이스가 존재하지만, 실제 플레이어 상호작용 처리에서는 `PlayerRay`가 태그별로 `DoorInteraction`, `ItemInteraction`, `MonitorInteraction`, `CofferInteraction`, `VentInteraction` 등을 직접 분기하고 각각의 컴포넌트를 가져오는 방식으로 구현되어 있습니다.

이 방식은 기능이 늘어날수록 `PlayerRay`에 조건문과 전용 메서드가 계속 추가되는 구조입니다.  
다음 프로젝트에서는 모든 상호작용 오브젝트가 공통 인터페이스를 구현하도록 만들고, 플레이어는 Raycast로 감지한 대상에서 `IInteraction`만 가져와 실행하는 방식으로 개선할 수 있습니다.

```csharp
if (Physics.Raycast(transform.position, transform.forward, out hit, distance))
{
    if (hit.transform.TryGetComponent<IInteraction>(out var interaction))
    {
        UIManager.Instance.DrawInteractText(interaction.InteractionText);

        if (Input.GetKeyDown(KeyCode.E) && !GameManager.Instance.IsPaused)
        {
            interaction.Interact();
        }
    }
}
